# Requirements Document: CoffeeCacaoSwap

## Introduction

CoffeeCacaoSwap is a specialized decentralized exchange (DEX) protocol built on the AgroChain ecosystem that enables permissionless token swaps and liquidity provision exclusively for Coffee and Cacao agricultural tokens. The protocol integrates with AgroChain's zero-knowledge certification system to ensure only ZK-certified Coffee (Arabica, Robusta/Conilon) and Cacao tokens can create liquidity pools. CoffeeCacaoSwap implements a constant product automated market maker (AMM) model with liquidity mining incentives through the CAFE governance token. The system is designed for deployment on CafeChain (primary) and Layer 2 networks (Polygon, Arbitrum) to provide low-cost, high-throughput trading of certified Coffee and Cacao tokens only.

## Glossary

- **CoffeeCacaoSwap_System**: The complete decentralized exchange protocol for Coffee and Cacao tokens including all smart contracts and frontend interfaces
- **Coffee_Token**: ERC20 tokens representing certified Coffee (Arabica or Robusta/Conilon) with AgroChain ZK certification
- **Cacao_Token**: ERC20 tokens representing certified Cacao with AgroChain ZK certification  
- **Agricultural_Token**: General term for Coffee_Token or Cacao_Token that has valid ZK_Certification
- **Trader**: A user who exchanges one token for another through the AMM
- **Liquidity_Provider**: A user who deposits token pairs into liquidity pools to earn trading fees
- **Farmer**: A user who stakes LP tokens in farms to earn CAFE token rewards
- **Token_Issuer**: An entity that has deployed an ERC20 token with ZK certification and seeks to create a liquidity pool
- **LP_Token**: ERC20 token representing proportional ownership of a liquidity pool
- **Pool**: A smart contract holding two tokens implementing the x*y=k constant product formula
- **Factory**: A smart contract that deploys new pools using CREATE2 and verifies token certification
- **Router**: A smart contract that handles multi-hop swaps and liquidity operations across pools
- **MasterChef**: A smart contract managing liquidity mining rewards distribution
- **CAFE_Token**: The native governance and utility token of CaféSwap with fixed supply and controlled emissions
- **Governance**: The decentralized decision-making system where CAFE holders vote on protocol parameters
- **ZK_Certification**: Proof generated by AgroChainCertificacoes contract verifying token compliance
- **Slippage**: The difference between expected and executed price due to market movement
- **Impermanent_Loss**: The temporary loss experienced by liquidity providers due to price divergence
- **CREATE2**: Ethereum opcode enabling deterministic contract deployment with predictable addresses

## Requirements

### Requirement 1: Coffee and Cacao Token Certification Verification

**User Story:** As a Coffee/Cacao Token_Issuer, I want to create a liquidity pool for my certified agricultural token, so that traders can access Coffee and Cacao tokens on the DEX

#### Acceptance Criteria

1. WHEN a Token_Issuer calls the pool creation function, THE Factory SHALL query the AgroChainCertificacoes contract to verify Coffee or Cacao token certification
2. IF the token is not a certified Coffee_Token or Cacao_Token, THEN THE Factory SHALL revert the transaction with error message "Only Coffee and Cacao tokens allowed"  
3. THE Factory SHALL verify both tokens in the pair are certified Coffee or Cacao tokens before pool creation
4. THE Factory SHALL emit a PoolCreated event containing pool address, token addresses, token types (COFFEE_ARABICA, COFFEE_ROBUSTA, or CACAO), and certification hashes
5. WHERE a Coffee or Cacao token certification expires, THE Pool SHALL continue operating but display a warning to users

### Requirement 2: Permissionless Coffee/Cacao Pool Creation

**User Story:** As a Coffee/Cacao Token_Issuer with certified tokens, I want to deploy a liquidity pool without requiring permission, so that I can list my Coffee or Cacao token immediately

#### Acceptance Criteria

1. WHEN a Token_Issuer calls createPool with two certified Coffee/Cacao token addresses, THE Factory SHALL deploy a new Pool using CREATE2
2. THE Factory SHALL accept pool pairs: COFFEE/USDC, CACAO/USDC, COFFEE/CACAO, or COFFEE/COFFEE (different varieties)
3. THE Factory SHALL compute the pool address deterministically based on sorted token addresses
4. IF a pool for the token pair already exists, THEN THE Factory SHALL revert with error "Pool already exists"  
5. THE Factory SHALL store the pool address in a mapping accessible by token pair
6. THE Pool SHALL initialize with zero liquidity and reserve ratio of 1:1 until first deposit

### Requirement 3: Liquidity Provision

**User Story:** As a Liquidity_Provider, I want to deposit token pairs into pools, so that I can earn trading fees proportional to my share

#### Acceptance Criteria

1. WHEN a Liquidity_Provider calls addLiquidity through the Router, THE Router SHALL calculate optimal token amounts maintaining current pool ratio
2. THE Router SHALL transfer both tokens from the Liquidity_Provider to the Pool
3. THE Pool SHALL mint LP_Tokens proportional to the deposited liquidity share
4. WHEN the first liquidity deposit occurs, THE Pool SHALL mint LP_Tokens equal to sqrt(amount0 * amount1) minus 1000 wei burned as minimum liquidity
5. IF the deposited ratio deviates from the current pool ratio, THEN THE Router SHALL return the excess tokens to the Liquidity_Provider
6. THE Pool SHALL update reserve amounts and emit a Mint event with liquidity details

### Requirement 4: Liquidity Removal

**User Story:** As a Liquidity_Provider, I want to withdraw my liquidity and collect earned fees, so that I can exit my position at any time

#### Acceptance Criteria

1. WHEN a Liquidity_Provider calls removeLiquidity through the Router, THE Router SHALL burn the specified amount of LP_Tokens
2. THE Pool SHALL calculate token amounts proportional to the burned LP_Token share
3. THE Pool SHALL transfer both tokens to the Liquidity_Provider
4. THE Pool SHALL update reserve amounts and emit a Burn event with withdrawal details
5. THE Pool SHALL include accumulated trading fees in the withdrawn amounts

### Requirement 5: Token Swapping

**User Story:** As a Trader, I want to swap Coffee and Cacao tokens with slippage protection, so that I can exchange certified agricultural tokens at fair market prices

#### Acceptance Criteria

1. WHEN a Trader calls swap through the Router with Coffee or Cacao input token and amount, THE Router SHALL calculate output amount using the constant product formula x*y=k
2. THE Router SHALL only accept swaps between certified Coffee_Tokens, Cacao_Tokens, and approved stablecoins (USDC)
3. THE Router SHALL deduct a 0.3% fee from the input amount before calculating output
3. IF the calculated output is less than the Trader's specified minimum amount, THEN THE Router SHALL revert with error "Insufficient output amount"
4. THE Router SHALL transfer the input token from the Trader to the Pool
5. THE Pool SHALL transfer the output token to the Trader
6. THE Pool SHALL update reserve amounts maintaining the constant product invariant
7. THE Pool SHALL emit a Swap event containing input amount, output amount, and recipient

### Requirement 6: Multi-Hop Routing

**User Story:** As a Trader, I want to swap Coffee and Cacao tokens that don't have a direct pool by routing through intermediate tokens, so that I can access the best available price for agricultural tokens

#### Acceptance Criteria

1. WHEN a Trader calls swap with a path containing multiple Coffee/Cacao token addresses, THE Router SHALL execute sequential swaps through the specified pools
2. THE Router SHALL support paths like COFFEE_ARABICA → USDC → CACAO or COFFEE_ROBUSTA → COFFEE_ARABICA
3. THE Router SHALL use the output of each swap as the input for the next swap in the path
3. THE Router SHALL calculate the final output amount considering all intermediate swap fees
4. IF any intermediate swap fails the slippage check, THEN THE Router SHALL revert the entire transaction
5. THE Router SHALL complete all swaps atomically in a single transaction

### Requirement 7: Price Impact Calculation

**User Story:** As a Trader, I want to see the price impact of my trade before execution, so that I can make informed trading decisions

#### Acceptance Criteria

1. THE Router SHALL provide a getAmountsOut view function calculating output amounts for a given input and path
2. THE Router SHALL provide a getAmountsIn view function calculating required input amounts for a desired output and path
3. THE Router SHALL calculate price impact as the percentage difference between spot price and execution price
4. THE Router SHALL account for the 0.3% trading fee in all price calculations

### Requirement 8: LP Token Staking

**User Story:** As a Farmer, I want to stake my Coffee/Cacao LP tokens in farms, so that I can earn CAFE token rewards in addition to trading fees from agricultural token pools

#### Acceptance Criteria

1. WHEN a Farmer calls stake on the MasterChef with LP_Token address and amount, THE MasterChef SHALL transfer LP_Tokens from the Farmer to itself
2. THE MasterChef SHALL record the staked amount and timestamp for the Farmer
3. THE MasterChef SHALL update the Farmer's pending CAFE rewards based on time elapsed since last action
4. THE MasterChef SHALL emit a Stake event containing Farmer address, LP_Token address, and amount

### Requirement 9: Farm Reward Distribution

**User Story:** As a Farmer, I want to claim my accumulated CAFE rewards, so that I can realize my farming earnings

#### Acceptance Criteria

1. WHEN a Farmer calls harvest on the MasterChef for a specific farm, THE MasterChef SHALL calculate pending CAFE rewards based on the reward rate and time staked
2. THE MasterChef SHALL mint new CAFE tokens according to the emission schedule controlled by Governance
3. THE MasterChef SHALL transfer the calculated CAFE rewards to the Farmer
4. THE MasterChef SHALL update the Farmer's last reward timestamp to the current block
5. THE MasterChef SHALL emit a Harvest event containing Farmer address, LP_Token address, and reward amount

### Requirement 10: LP Token Unstaking

**User Story:** As a Farmer, I want to unstake my LP tokens from farms, so that I can remove my liquidity or move to different farms

#### Acceptance Criteria

1. WHEN a Farmer calls unstake on the MasterChef with LP_Token address and amount, THE MasterChef SHALL automatically harvest pending rewards
2. THE MasterChef SHALL transfer the specified LP_Token amount back to the Farmer
3. THE MasterChef SHALL update the Farmer's staked balance
4. IF the unstake amount exceeds the staked balance, THEN THE MasterChef SHALL revert with error "Insufficient staked balance"
5. THE MasterChef SHALL emit an Unstake event containing Farmer address, LP_Token address, and amount

### Requirement 11: CAFE Token Governance Rights

**User Story:** As a CAFE holder, I want to vote on protocol parameters, so that I can participate in decentralized governance

#### Acceptance Criteria

1. WHEN a CAFE holder holds tokens, THE CAFE_Token SHALL grant voting power equal to the token balance
2. THE CAFE_Token SHALL support delegation allowing holders to delegate voting power to another address
3. THE CAFE_Token SHALL track voting power at specific block numbers for snapshot-based governance
4. THE CAFE_Token SHALL emit a DelegateChanged event when voting delegation occurs

### Requirement 12: Governance Proposal Creation

**User Story:** As a CAFE holder with sufficient tokens, I want to create governance proposals to change protocol parameters, so that the community can vote on improvements

#### Acceptance Criteria

1. WHEN a CAFE holder with at least 1% of total supply calls propose on the Governance contract, THE Governance SHALL create a new proposal
2. THE Governance SHALL assign a unique proposal ID and set the voting period to 7 days
3. THE Governance SHALL require proposals to include a description and executable function calls
4. IF the proposer holds less than 1% of supply, THEN THE Governance SHALL revert with error "Insufficient proposal threshold"
5. THE Governance SHALL emit a ProposalCreated event containing proposal ID, proposer, and description

### Requirement 13: Governance Voting

**User Story:** As a CAFE holder, I want to vote on active proposals, so that I can express my opinion on protocol changes

#### Acceptance Criteria

1. WHEN a CAFE holder calls vote on the Governance contract with proposal ID and vote direction, THE Governance SHALL record the vote weighted by the holder's voting power at proposal snapshot
2. THE Governance SHALL support three vote options: For, Against, and Abstain
3. IF the voting period has ended, THEN THE Governance SHALL revert with error "Voting period ended"
4. IF the holder has already voted, THEN THE Governance SHALL revert with error "Already voted"
5. THE Governance SHALL emit a VoteCast event containing voter address, proposal ID, vote direction, and voting power

### Requirement 14: Governance Proposal Execution

**User Story:** As any user, I want to execute a successful governance proposal after the voting period ends, so that approved changes take effect

#### Acceptance Criteria

1. WHEN the voting period ends and a proposal has more For votes than Against votes, THE Governance SHALL mark the proposal as succeeded
2. WHEN any user calls execute on a succeeded proposal, THE Governance SHALL execute the encoded function calls via delegatecall
3. THE Governance SHALL require a quorum of at least 10% of total supply voting For to execute
4. IF quorum is not met, THEN THE Governance SHALL mark the proposal as defeated
5. THE Governance SHALL emit a ProposalExecuted event containing proposal ID and execution timestamp

### Requirement 15: CAFE Token Emission Control

**User Story:** As the Governance system, I want to control CAFE token emission rates for farms, so that the community can adjust inflation based on protocol needs

#### Acceptance Criteria

1. THE Governance SHALL have exclusive permission to call setRewardRate on the MasterChef contract
2. WHEN setRewardRate is called, THE MasterChef SHALL update the CAFE tokens minted per block for liquidity mining
3. THE MasterChef SHALL apply the new rate starting from the next block
4. THE CAFE_Token SHALL enforce a maximum supply cap preventing unlimited inflation
5. IF minting would exceed the supply cap, THEN THE CAFE_Token SHALL revert with error "Supply cap exceeded"

### Requirement 16: Multi-Chain Deployment

**User Story:** As a Trader, I want to use CoffeeCacaoSwap on multiple chains, so that I can choose the network with the lowest fees and best liquidity for Coffee and Cacao tokens

#### Acceptance Criteria

1. THE CoffeeCacaoSwap_System SHALL deploy identical contract bytecode on CafeChain, Polygon, and Arbitrum
2. THE Factory SHALL use CREATE2 to generate identical pool addresses across all chains for the same Coffee/Cacao token pairs
3. WHERE cross-chain liquidity bridging is implemented, THE Router SHALL verify bridge integrity before executing cross-chain swaps
4. THE CaféSwap_System SHALL maintain independent liquidity pools on each chain

### Requirement 17: Security - Reentrancy Protection

**User Story:** As a Liquidity_Provider, I want protection against reentrancy attacks, so that my funds are secure

#### Acceptance Criteria

1. THE Pool SHALL implement a reentrancy guard preventing recursive calls during swap, mint, and burn operations
2. THE Router SHALL implement a reentrancy guard on all external functions
3. THE MasterChef SHALL implement a reentrancy guard on stake, unstake, and harvest functions
4. IF a reentrant call is detected, THEN THE contract SHALL revert with error "Reentrancy detected"

### Requirement 18: Security - Integer Overflow Protection

**User Story:** As any user, I want protection against mathematical errors, so that calculations are always accurate

#### Acceptance Criteria

1. THE CaféSwap_System SHALL use Solidity 0.8.0 or higher with built-in overflow protection
2. WHERE custom mathematical operations are required, THE contracts SHALL use SafeMath library or checked arithmetic
3. THE Pool SHALL validate that reserve updates maintain the constant product invariant within acceptable precision limits

### Requirement 19: Gas Optimization

**User Story:** As a Trader, I want low transaction costs, so that trading small amounts remains profitable

#### Acceptance Criteria

1. THE Pool SHALL optimize storage layout to minimize SSTORE operations
2. THE Router SHALL batch multiple token transfers in single external calls where possible
3. THE CaféSwap_System SHALL target maximum gas cost of 150,000 gas for single-hop swaps on Layer 2 networks
4. THE Pool SHALL use uint112 for reserve storage to pack multiple reserves in single storage slot

### Requirement 20: Frontend Wallet Integration

**User Story:** As a Trader, I want to connect my Web3 wallet to the CoffeeCacaoSwap interface, so that I can interact with the Coffee and Cacao trading protocol

#### Acceptance Criteria

1. THE Frontend SHALL support MetaMask, WalletConnect, and Coinbase Wallet connection methods
2. WHEN a user connects a wallet, THE Frontend SHALL detect the connected network and display appropriate pool data
3. IF the user is on an unsupported network, THEN THE Frontend SHALL prompt the user to switch networks
4. THE Frontend SHALL display the user's token balances and LP positions after wallet connection

### Requirement 21: Frontend Price Charts

**User Story:** As a Trader, I want to see historical price charts for Coffee and Cacao token pairs, so that I can analyze agricultural market trends before trading

#### Acceptance Criteria

1. THE Frontend SHALL display candlestick or line charts showing price history for the past 24 hours, 7 days, and 30 days
2. THE Frontend SHALL update price data every 30 seconds while the page is active
3. THE Frontend SHALL calculate prices from Pool reserve ratios and historical Swap events
4. THE Frontend SHALL display 24-hour volume, total liquidity, and fee APR for each pool

### Requirement 22: Frontend Transaction Confirmation

**User Story:** As a Trader, I want to review transaction details before signing, so that I can verify parameters are correct

#### Acceptance Criteria

1. WHEN a user initiates a swap, THE Frontend SHALL display a confirmation modal showing input amount, expected output, minimum output, price impact, and estimated gas cost
2. THE Frontend SHALL warn the user if price impact exceeds 5%
3. WHEN a user confirms the transaction, THE Frontend SHALL call the Router with the user's specified slippage tolerance
4. THE Frontend SHALL display transaction status with links to the block explorer

### Requirement 23: Smart Contract Upgradeability

**User Story:** As the Governance system, I want the ability to upgrade contract logic if critical bugs are found, so that user funds remain protected

#### Acceptance Criteria

1. WHERE upgradeability is required, THE CaféSwap_System SHALL implement transparent proxy pattern with ProxyAdmin controlled by Governance
2. THE Governance SHALL require a 48-hour timelock before executing upgrade transactions
3. THE CaféSwap_System SHALL emit an Upgraded event containing old implementation address and new implementation address
4. WHERE contracts are immutable, THE Factory SHALL allow deploying new Router versions while maintaining existing pools

### Requirement 24: Emergency Pause Mechanism

**User Story:** As the Governance system, I want to pause protocol operations if an exploit is detected, so that further damage can be prevented

#### Acceptance Criteria

1. THE Router SHALL implement a pausable pattern with pause and unpause functions controlled by Governance
2. WHILE the protocol is paused, THE Router SHALL revert all swap and liquidity operations with error "Protocol paused"
3. WHILE the protocol is paused, THE Liquidity_Providers SHALL retain the ability to withdraw liquidity
4. THE Governance SHALL require a 24-hour timelock before unpausing the protocol after an emergency pause

### Requirement 25: Fee Collection and Distribution

**User Story:** As a Liquidity_Provider, I want to automatically earn my share of trading fees, so that I am compensated for providing liquidity

#### Acceptance Criteria

1. WHEN a Swap occurs, THE Pool SHALL deduct 0.3% of the input amount as a trading fee
2. THE Pool SHALL add the fee to the reserves increasing the constant product k
3. WHEN a Liquidity_Provider removes liquidity, THE Pool SHALL include accumulated fees proportional to their LP_Token share
4. THE Pool SHALL track cumulative fees for analytics and reporting purposes

### Requirement 26: Pool Reserve Synchronization

**User Story:** As a Liquidity_Provider, I want pool reserves to accurately reflect token balances, so that the AMM pricing remains accurate

#### Acceptance Criteria

1. THE Pool SHALL store reserve amounts as cached state variables updated after each swap, mint, or burn
2. THE Pool SHALL provide a sync function that updates reserves to match actual token balances
3. WHEN sync is called, THE Pool SHALL handle token balance discrepancies caused by direct transfers
4. THE Pool SHALL emit a Sync event containing updated reserve amounts after each state change

### Requirement 27: Price Oracle Integration

**User Story:** As a smart contract developer, I want to read time-weighted average prices from pools, so that I can build price-dependent applications

#### Acceptance Criteria

1. THE Pool SHALL track cumulative price for both tokens using the reserve ratio
2. THE Pool SHALL update cumulative price on every block where a swap, mint, or burn occurs
3. THE Pool SHALL provide view functions returning current cumulative prices
4. WHERE the pool has been manipulated via flash loan, external contracts SHALL use time-weighted average price over at least 10 minutes

### Requirement 28: Liquidity Migration

**User Story:** As a Liquidity_Provider, I want to migrate my liquidity from other DEXes to CaféSwap, so that I can consolidate my positions

#### Acceptance Criteria

1. WHERE a migration tool is implemented, THE Router SHALL support removing liquidity from external DEX pools and adding to CaféSwap pools in a single transaction
2. THE Router SHALL calculate optimal amounts to minimize token leftovers after migration
3. THE Router SHALL require user approval for the external LP tokens before migration
4. IF migration would result in unfavorable price impact, THEN THE Router SHALL revert with error "Migration price impact too high"

### Requirement 29: Analytics and Metrics

**User Story:** As a protocol operator, I want to track key metrics like TVL, volume, and active users, so that I can monitor protocol health

#### Acceptance Criteria

1. THE Factory SHALL emit events for all pool creations with indexed token addresses
2. THE Pool SHALL emit events for all swaps, mints, and burns with indexed user addresses
3. THE MasterChef SHALL emit events for all stake, unstake, and harvest actions
4. WHERE analytics infrastructure is deployed, THE CaféSwap_System SHALL support querying historical events via standard blockchain indexers

### Requirement 30: Token Whitelisting for Farms

**User Story:** As the Governance system, I want to whitelist specific Coffee/Cacao LP tokens for farming rewards, so that incentives align with agricultural protocol goals

#### Acceptance Criteria

1. WHEN Governance calls addFarm on the MasterChef with a Coffee/Cacao LP_Token address and allocation points, THE MasterChef SHALL enable CAFE rewards for that farm
2. THE MasterChef SHALL prioritize Coffee_Arabica, Coffee_Robusta, and Cacao LP tokens for higher allocation points
3. THE MasterChef SHALL distribute rewards proportionally based on each Coffee/Cacao farm's allocation points
3. THE Governance SHALL have exclusive permission to adjust allocation points for existing farms
4. THE MasterChef SHALL enforce a maximum of 50 active farms to limit gas costs

## Constraints

1. The CoffeeCacaoSwap_System SHALL be compatible with Ethereum Virtual Machine (EVM) chains
2. The system SHALL ONLY accept certified Coffee (Arabica, Robusta/Conilon) and Cacao tokens with valid AgroChain ZK certification  
3. Smart contracts SHALL be written in Solidity version 0.8.0 or higher
4. The system SHALL integrate with the existing AgroChainCertificacoes contract without modifying its interface
5. The CAFE_Token total supply SHALL be capped at 100,000,000 tokens  
6. The protocol SHALL reject any tokens that are not Coffee_Token or Cacao_Token types
7. The protocol SHALL minimize governance centralization by requiring timelock delays on critical operations
8. All smart contracts SHALL be verified on blockchain explorers for transparency

## Dependencies

1. **AgroChainCertificacoes.sol**: Smart contract providing token certification verification via ZK proofs
2. **OpenZeppelin Contracts**: Library providing secure, audited implementations of ERC20, Ownable, ReentrancyGuard, and Pausable patterns
3. **Solidity Compiler**: Version 0.8.0 or higher with optimizer enabled
4. **Hardhat or Foundry**: Development framework for smart contract compilation, testing, and deployment
5. **Web3.js or Ethers.js**: JavaScript library for blockchain interaction from frontend
6. **React.js**: Frontend framework for building the user interface
7. **WalletConnect SDK**: Library for multi-wallet connection support
8. **The Graph Protocol**: Decentralized indexing service for querying blockchain events (optional for analytics)
9. **IPFS**: Decentralized storage for hosting frontend interface (optional)
10. **Chainlink Price Feeds**: Oracle network for external price data (if needed for governance or farms)
